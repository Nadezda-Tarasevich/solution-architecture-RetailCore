# Ключевые требования к системе RetailCore

#### 

#### Функциональные требования (ФТ)



ФТ-01. Система должна хранить полную, неизменяемую хронологию событий по каждому заказу: какие изменения произошли, когда, по какой причине и какой компонент системы/пользователь их инициировал. История должна быть доступна для внутренних систем и уполномоченных подразделений (поддержка, аналитика, финансы), но не для внешних клиентов.

ФТ-02. Система должна поддерживать жизненный цикл заказа с корректными переходами между состояниями. Система должна поддерживать формально описанную модель состояний заказа с валидными переходами между ними. Фактическое поведение системы должно соответствовать документации. Все «отклонения» должны быть явно зафиксированы как исключения, а не как часть стандартного потока.

ФТ-03 Система должна поддерживать несколько представлений статусов заказа с автоматическим маппингом между ними: для клиента (абстрактное, понятное), для оператора поддержки (детализированное, с контекстом), для внешних систем и партнёров (каноническое, по протоколу).

ФТ-04. Система должна распознавать типовые отклонения выполнения заказа (зависший статус, рассинхронизация с партнёром, частичная отмена, превышение времени ожидания ответа от внешней системы) и автоматически запускать предопределённый сценарий: повторная попытка (retry), эскалация в нужную очередь поддержки, отправка уведомления заинтересованным сторонам.

ФТ-05. Оператор поддержки должен видеть по каждому заказу: текущее детализированное состояние, причину отклонения (если применимо), следующий запланированный системой шаг, возможность направить заказ в нужный контур обработки или эскалировать его.

ФТ-06. Процесс оформления заказа (расчёт стоимости, применение скидок, выбор доставки и оплаты) должен быть защищён от влияния изменений в других частях системы.

ФТ-07. Система должна поддерживать подключение новых коммерческих сценариев (персонализированные предложения, гибкие промо-акции, новые каналы продаж) через выделенный API-слой или плагинную архитектуру без необходимости модификации ядра и без ручных обходов.Новые промо, правила доставки и сценарии должны включаться/выключаться через механизм feature toggles без выкатки кода.

ФТ-08. Система должна поддержать единую логику обработки заказа, независящей от специфики канала (сайт, мобильное приложение, маркетплейс).

ФТ-09. Система должна предоставлять единый механизм приёма и обработки внешних событий (платежи, логистические статусы, обновления от маркетплейсов) с обеспечением: идемпотентности повторных/дублирующихся событий, контроля порядка обработки и корреляции асинхронных обновлений, применения событий к актуальному состоянию заказа.

ФТ-10. Система должна предоставлять консистентные данные о заказах для всех подразделений (логистика, финансы, маркетинг, аналитика) из единого источника, исключая расхождения в отчётности.



#### Нефункциональные требования (НФТ)



НФТ-01.  Для любого типового коммерческого изменения (новая акция, правило доставки, партнёрский сценарий) архитектура системы должна позволять заранее оценить объём работ, зоны влияния, риски и потенциальные побочные эффекты.

НФТ-02. Все изменения платформы должны выполняться поэтапно. Каждый этап должен: быть обратимым (возможность отката), сохранять или улучшать наблюдаемость системы, приносить измеримую бизнес-ценность. Ухудшение прозрачности на переходном этапе недопустимо.

НФТ-03. Система должна предоставлять возможность добавлять новые каналы продаж, внешних партнёров и коммерческие сценарии через механизмы расширения (API, плагины, конфигурация) без необходимости изменять ядро платформы.

НФТ-04. Оформление заказа, оплата и подтверждение должны оставаться работоспособными при сбоях или деградации в других подсистемах. Сбой в некритичной функции (например, расчёт скидки для определённого партнёра, интеграция с конкретным маркетплейсом) не должен блокировать или замедлять базовый процесс оформления заказа.

НФТ-05. Изменения в API платформы не должны нарушать существующие интеграции с внешними партнёрами (маркетплейсы, платёжные провайдеры, службы доставки). Должна поддерживаться версионность API и объявление устаревших методов (deprecation policy) с достаточным переходным периодом.

НФТ-06. Система должна сохранять предсказуемое поведение и целевые показатели производительности на сезонных пиках (распродажи, рекламные кампании). Требуется возможность горизонтального масштабирования наиболее нагруженных компонентов.

НФТ-07. Зависшие процессы, потерянные сообщения, таймауты внешних вызовов и другие сбои должны автоматически обнаруживаться системой. Для каждого класса сбоев должен быть определён сценарий восстановления: повторная попытка с экспоненциальной задержкой (retry), отправка в очередь недоставленных сообщений (DLQ), эскалация оператору.

НФТ-08.  Для каждого заказа система должна обеспечивать доступ к: метрикам времени прохождения каждого этапа обработки, логам всех ключевых событий с контекстом, трассировке запросов, проходящих через все сервисы и компоненты. Время диагностики проблемы не должно превышать заданного SLA.



#### Ограничения (ОГР)



ОГР-01. Все изменения должны происходить в работающей системе (in-production) поэтапно, с контролируемым риском и обязательной возможностью отката.

ОГР-02. Невозможно одномоментно отказаться от монолитного ядра, Oracle или других legacy-компонентов, особенно если они обслуживают критичные операции. Замена возможна только постепенно, с сохранением обратной совместимости.

ОГР-03. Ресурсы Oracle близки к пределу. База данных является фактором, ограничивающим и производительность, и скорость развития.

ОГР-04. Система развёрнута на физических серверах. Виртуализация используется ограниченно. Наращивание ресурсов требует времени, закупок и согласований.

ОГР-05.Java-монолит + сервисы на Python и .NET. Разные подходы к разработке и взаимодействию между командами.

ОГР-06. Взаимодействие между компонентами реализовано разными способами: прямые вызовы, обмен через общую БД, асинхронные механизмы. Часть интеграций не документирована.

ОГР-07. Зарубежные технологии (включая Oracle) должны быть заменены, но не ценой остановки ключевых процессов.

ОГР-08. Существующие архитектурные схемы и документация не всегда отражают фактическое поведение системы. Знания распределены и часто не формализованы.

ОГР-09. Финансирование трансформации выделяется поэтапно. Каждый этап должен быть экономически обоснован и приносить измеримую бизнес-ценность.

ОГР-10. Ни один этап не должен приводить к ухудшению базовой конверсии заказа, скорости обработки или прозрачности статусов для клиента.

ОГР-11. Маркетплейсы, платёжные провайдеры и службы доставки могут менять свои API и протоколы без предупреждения.



#### Допущения (ДОП)

ДОП-01. Бизнес не требует одномоментного перепроектирования системы. Ценность представляет реалистичный поэтапный план с промежуточными результатами, а не архитектурная «красота» сама по себе.

ДОП-02. Выбор технологий и подходов должен быть привязан к измеримым бизнес-результатам, а не к технической «правильности» или модным трендам.

ДОП-03. Устойчивость checkout, оплаты и подтверждения заказа важнее скорости внедрения новых коммерческих функций.
