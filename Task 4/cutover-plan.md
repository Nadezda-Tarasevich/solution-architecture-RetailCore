# Cutover Plan — RetailCore

#### Назначение документа

Документ описывает процедуры безопасного переключения между состояниями системы в ходе инкрементальной миграции RetailCore. 

### Общие принципы cutover

Поэтапность: любой cutover выполняется пошагово: сначала мониторинг (логирование без действий), потом пилот (один сценарий / один партнёр), потом масштабирование (все сценарии).

Наблюдаемость: до cutover должны быть настроены метрики и дашборды для мониторинга эффекта в реальном времени.

Обратимость: каждый cutover должен иметь план отката. Время отката не должно превышать 1 час.

Go / No Go: каждый cutover выполняется по решению владельца после проверки критериев готовности.

Коммуникация: о всех плановых cutover уведомляются заинтересованные стороны за 24 часа. Об экстренных — немедленно.



#### Cutover: Circuit Breaker в Checkout API

**Этап1**:  Пилотный контур

**Владелец**: Техлид монолита

**Риск**: CB может добавить задержку при штатной работе checkout

**Критерии готовности**: Нагрузочное тестирование CB пройдено (p95 ≤ 2с). Метрики p95 checkout настроены и доступны в реальном времени. Дашборд мониторинга готов. План отката утверждён.

**Шаги включения** 

1.: Включить CB в режиме мониторинга (логирование всех срабатываний, но без изменения поведения) — 1–2 дня. 

2\. Проверить логи: нет ложных срабатываний. 

3\. Включить CB в активном режиме для пилотного сценария (один маршрут доставки). 

4\. Мониторинг 1 день. 

5\. Включить CB для всех сценариев.

**Мониторинг**: p95 checkout (цель: ≤ 2с). Количество срабатываний CB. Количество заказов, переведённых в статус ожидания.

**План отката:** Отключить CB в Checkout API. Вернуться к синхронным вызовам. Время отката: ≤ 30 минут.

**Экстренная остановка**: p95 checkout > 3с в течение 10 минут после включения — откат немедленно.

**Go / No Go решение:** Техлид монолита + руководитель эксплуатации



#### Cutover: Event Stor

**Этап 1**. Пилотный контур

**Владелец**: Техлид монолита

**Риск**: Рассинхронизация Event Store с Oracle. Потеря событий. Некорректная фиксация истории заказа.

**Критерии готовности**: Event Store schema утверждена. Коннекторы к источникам событий (OrderProcessingService, Checkout API, StatusEngine) реализованы и протестированы в изоляции. Настроена сверка ключевых событий с Oracle. Дашборд мониторинга готовности Event Store готов.

**Шаги включения**

1\. Включить Event Store в режиме параллельной записи (события фиксируются и в Oracle, и в Event Store, но чтение оператором пока из Oracle) — 3 дня. 

2\. Ежечасовая сверка событий Event Store с Oracle — расхождение не более 1%. 

3\. Включить консоль Event Store для пилотной группы операторов (2–3 человека) — 1 неделя. 

4\. Собрать обратную связь от операторов. 

5\. Включить Event Store как основной источник для всех операторов. 

6\. Переключить Exception Handler на чтение из Event Store (только после стабилизации).

**Мониторинг:** Расхождение событий Event Store с Oracle (цель: ≤ 1%). Количество событий, записанных в Event Store. Количество событий, прочитанных операторами из консоли Event Store. Время задержки записи события.

**План отката**: Отключить консоль Event Store для операторов. Вернуть операторов к старому интерфейсу (чтение из Oracle и логов). Event Store продолжает работать в фоновом режиме для накопления данных. Время отката: ≤ 15 минут.

**Экстренная остановка:** Расхождение Event Store с Oracle > 5% — остановить использование Event Store как источника для операторов, переключиться на Oracle. Потеря событий (пропуск более 1% критических событий за час) — остановить запись, чинить коннекторы.

**Go / No Go решение:** Техлид монолита + руководитель поддержки



#### Cutover: Async Retry для платежей

**Этап 2**: Стабилизация сценария

**Владелец**: Техлид интеграций

**Риск**: Дублирующиеся платежи при отсутствии идемпотентности

**Критерии готовности**: Проверена идемпотентность платёжного провайдера. Внедрён idempotency key на стороне RetailCore. CB уже активен. Event Store фиксирует все попытки retry. Дашборд мониторинга платежей готов.

**Шаги включения**	

1\. Включить Async Retry в режиме мониторинга (логирование retry без выполнения) — 1 день. 

2\. Проверить: сценарии срабатывания корректны. 

3\. Включить Async Retry для одного платёжного провайдера (пилот). 

4\. Мониторинг 2 дня — проверка отсутствия дублей. 

5\. Включить Async Retry для всех платёжных провайдеров.

**Мониторинг**: Количество retry. Количество успешных retry. Количество дублей платежей. Время восстановления заказа после сбоя.

**План отката**: Отключить Async Retry для платежей. Заказы со статусом «Ожидание оплаты» передать операторам для ручной обработки. Время отката: ≤ 15 минут.

**Экстренная остановка**: Обнаружение хотя бы одного двойного списания — немедленная остановка Async Retry и блокировка повторных попыток до выяснения причин.

**Go / No Go решение:** Техлид интеграций + руководитель поддержки



#### Cutover: Async Retry для доставки

**Этап2:** Стабилизация сценария

**Владелец**: Техлид интеграций

**Риск**: Дублирующиеся заказы у службы доставки

**Критерии готовности**: Проверена возможность идемпотентности у службы доставки. Аналогично платежам — idempotency key. Event Store готов.

**Шаги включения**	

1\. Мониторинг — 1 день. 

2\. Пилот — один маршрут / одна ТК. 

3\. Мониторинг 2 дня. 

4\. Включение для всех маршрутов.

**Мониторинг**: Количество retry. Количество успешных retry. Количество дублей заказов. Время восстановления заказа.

**План отката**: Отключить Async Retry для доставки. Заказы со статусом «Уточнение доставки» передать операторам.

**Экстренная остановка**: Дубль заказа в ТК — немедленная остановка.

**Go / No Go решение**: Техлид интеграций + руководитель логистики





#### Cutover: Exception Handler (топ-3 исключений)

**Этап2**: Стабилизация сценария

**Владелец**: Техлид монолита

**Риск**: неверная классификация исключений и применение некорректных сценариев

**Критерии готовности:** Event Store стабилен (расхождение с Oracle ≤ 1%). Сценарии для топ-3 исключений утверждены руководителем поддержки. Режим мониторинга EH готов.

**Шаги включения**	

1\. Включить EH в режиме мониторинга (логирование решений без автоматических действий) — 1 неделя. 

2\. Проверить accuracy классификации. 

3\. Включить EH в режиме авто-действий только для retry (без эскалации) — 1 неделя. 

4\. Включить полный цикл EH (retry + эскалация).

**Мониторинг:** Доля исключений, распознанных EH. Доля верных (TP) vs неверных (FP) решений. Доля заказов, обработанных автоматически.

**План отката**: Отключить EH. Вернуться к ручной обработке исключений. Время отката: ≤ 1 минута (изменение toggle).

**Экстренная остановка**: Доля некорректных авто-действий > 10% — откат к режиму мониторинга.

**Go / No Go решение:** Техлид монолита + руководитель поддержки





#### Cutover: Feature Toggles для промо



**Этап3**: Масштабирование

**Владелец**: Бизнес-спонсор

**Риск:** Некорректное применение промо-правил или неверные настройки

**Критерии готовности**: Интерфейс FT протестирован с маркетологом. Пилотные сценарии утверждены. Метрики времени запуска промо настроены.

**Шаги включения**	

1\. Пилот — 2–3 простых сценария (скидка на категорию, бесплатная доставка) с одним маркетологом. 

2\. Мониторинг 1 неделя — проверка корректности применения. 

3\. Расширение — все маркетологи, все типы промо.

**Мониторинг**: Время запуска промо. Количество ошибок при настройке. Доля промо, запущенных через FT (vs через код).

**План отката**: Отключить FT для промо. Вернуться к запуску через код. Время отката: ≤ 30 минут.

**Экстренная остановка**: Некорректное применение промо (неверная скидка) — отключить конкретный toggle.

**Go / No Go решение**: Бизнес-спонсор + руководитель маркетинга



#### Cutover: Переключение Batch-пайплайнов на Analytics DB

**Этап3**: Масштабирование

**Владелец:** Техлид аналитики

**Риск**: Некорректные отчёты при переключении

**Критерии готовности**: Analytics DB развёрнута. Репликация данных из Oracle настроена. Тестовая сверка отчётов пройдена.

**Шаги включения**	

1\. Параллельный прогон (дуалинг): batch-пайплайны читают данные из Oracle и из Analytics DB одновременно, результаты сравниваются. 

2\. Сверка отчётов за 1 неделю — расхождение ≤ 0.1% (допустимая задержка). 

3\. Переключение batch-пайплайнов на чтение только из Analytics DB. 

4\. Мониторинг 1 неделя. 5. Блокировка прямого доступа BI к Oracle.

**Мониторинг**: Загрузка Oracle (CPU/I/O). Корректность отчётов. Время выполнения batch-пайплайнов.

**План отката**: Вернуть batch-пайплайны на чтение из Oracle. Время отката: ≤ 30 минут.

**Экстренная остановка**: Расхождение отчётов > 1% — откат. Загрузка Oracle не снизилась через 2 недели — анализ причин.

**Go / No Go решение**: Техлид аналитики + руководитель эксплуатации
