### 1\. Краткое резюме roadmap

Миграция выполняется инкрементально, потому что полная замена монолита (Big Bang) невозможна из-за ограничения «нельзя останавливать бизнес». Сначала команда фиксирует базовые метрики AS-IS и подготавливает Event Store для наблюдаемости, затем внедряет Circuit Breaker в Checkout API — первый безопасный переход, который защищает критический контур от сбоев внешних систем. После этого стабилизируется сценарий асинхронных повторов (Async Retry) и автоматической обработки исключений (Exception Handler). Параллельно внедряются Feature Toggles для управления акциями и правилами, а также выносится аналитика из операционной Oracle. Такой порядок выбран из-за зависимостей: Event Store необходим как источник данных для Exception Handler, а Circuit Breaker — как основа для Async Retry. Основные риски roadmap связаны с корректностью работы Circuit Breaker (не должен добавлять задержку), идемпотентностью Async Retry (не должен создавать дубли) и принятием новых инструментов пользователями (Feature Toggles).

### 3\. Принципы построения roadmap

1\. До начала любых изменений зафиксировать базовые метрики (p95 checkout, загрузка Oracle, время диагностики, время запуска промо).

2\. Circuit Breaker — первый шаг, защищающий checkout. Только после его стабилизации — Async Retry и Exception Handler.

3\. Feature Toggles — сначала для 2–3 простых сценариев, потом для всех. Async Retry — сначала для одного маршрута доставки, потом для всех.

4\. Новые статусы («Ожидание оплаты», «Уточнение доставки») должны быть согласованы и протестированы до включения автоматических переходов.

5\. Перед выносом аналитики из Oracle — инвентаризация всех потребителей данных и их требований.

## 12\. Проверка качества roadmap

Перед сдачей проверьте, что:

* \[х ] roadmap связан с точками трансформации из `transformation.md`;
* \[ х] есть стартовое состояние, промежуточные состояния и TO-BE;
